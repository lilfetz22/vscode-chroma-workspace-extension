### vscode/Tag.ts

#### [SUGGESTION] `nameToHex` fallback in the API path is unreachable
- **Location:** API branch of `addTag`, `color = normalizeHex(arg.color) || nameToHex(arg.color);`
- **Issue:** The local `normalizeHex` delegates to `utilNormalizeHex`, which already resolves
  CSS color names via `CSS_COLOR_MAP`. The `nameToHex` fallback can therefore never produce a
  value that `normalizeHex` did not. It is harmless but implies a second resolution strategy
  that does not exist.
- **Suggestion:**
  ```ts
  color = normalizeHex(arg.color);
  ```

#### [SUGGESTION] Duplicate-name rejection is inconsistent with the interactive paths
- **Location:** API branch of `addTag`, duplicate check via `getAllTags().some(...)`
- **Issue:** The interactive `addTag` prompt and `selectOrCreateTags` both allow creating a
  tag whose name collides with an existing one. The API now rejects it. The stricter API
  behavior is defensible (an automated caller cannot see the existing list), but the
  divergence is undocumented.
- **Suggestion:** Either note the API-only constraint in the README command table, or lift the
  check into a shared helper used by both paths so the rule is uniform:
  ```ts
  function assertTagNameAvailable(name: string): void {
      if (getAllTags().some(t => t.name.toLowerCase() === name.toLowerCase())) {
          throw new Error(`A tag named "${name}" already exists`);
      }
  }
  ```
